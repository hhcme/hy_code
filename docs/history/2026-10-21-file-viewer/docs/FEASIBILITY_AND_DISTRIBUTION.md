初始研究：2026-10-19；范围更新：2026-10-21。本文区分平台规则、工程建议和待核实问题，不代表已通过审核、取得许可或确认免备案。

## 1. 技术栈与格式实现

当前方向是共享 Rust 文件处理核心 + 各端原生 UI/系统适配。Apple 延续已有 SwiftUI/UniFFI 骨架；Windows、Linux、Android、HarmonyOS NEXT 的建议框架、绑定和验证状态见[技术设计](TECH_DESIGN.md)。优先 Rust 库，必要时用成熟 C/C++ 引擎及原生预览、播放、分享能力；“优先 Rust”不代表把每种语言分析器重写为 Rust。

Mac 侧保留仅 Apple Silicon 的约束。当前脚本仅输出 macOS 切片；iOS 设备/模拟器及其他端需要自己的 Rust 目标、SDK、绑定与打包链，不再用 Apple 两个目标概括整个项目。全端统一的是领域能力和接口，实际支持格式仍逐引擎、逐平台记录。

建议采用可独立维护的格式模块：共享文件导入、浏览、任务、缓存和导出能力，各类格式使用合适的预览或解析引擎。模块化是内部组织方式，不等于允许从网络安装新代码。

文件编辑、高亮、语义服务分层，详见[代码编辑与语言服务](CODE_INTELLIGENCE.md)。桌面可按权限和渠道接入独立 LSP；移动端不默认拥有外部 SDK、Node/JVM、子进程或运行时下载能力。源码公开、服务能运行和允许随应用分发是三个不同检查项。

可行性基础：

- Apple Quick Look 提供常见办公文档、图片、文本、PDF、音视频和部分三维内容的预览基础，但不能据此保证每种文件版本及复杂内容均完整兼容。
- PDF、网页、媒体、电子书、压缩包、专业设计和 CAD 等类别可能需要不同的系统能力或第三方引擎，不能预设一个免费引擎覆盖全部格式。
- 归档库通常可覆盖多种格式，但读取与写入格式不同，加密、分卷等能力也需要逐项确认。
- 系统预览是否满足产品体验，需要用目标系统上的真实文件验证，不能只根据文档里的格式名称做结论。

参考：[Apple Quick Look](https://developer.apple.com/documentation/QuickLook)、[libarchive](https://libarchive.org/)、[Apple 媒体类型与编码可播放性](https://developer.apple.com/documentation/avfoundation/avurlasset/audiovisualmimetypes%28%29)。

第三方引擎选型时应记录商业使用和分发条件。使用开源库不自动代表任何闭源收费应用都能无条件集成，也不代表必须购买收费 SDK。

RAR 是重要例子：unRAR 源码具有不得用于重建 RAR 压缩算法的限制。支持 RAR 解压不能推导为能够创建 RAR。参考：[7-Zip 官方许可](https://www.7-zip.org/license.txt)。

## 2. 原生模块与可下载扩展

以下针对 App Store / Mac App Store，不推广为所有平台、所有渠道的结论。Apple 保留此前先只走应用商店、不考虑商店外公证分发的约束；Windows/Linux/Android/鸿蒙渠道待定。当前以产品开发优先，各端临近发布分别核对规则，不能直接复用 HyHub 的直发包结论。

| 内容 | 讨论结论 |
| --- | --- |
| 新的原生格式引擎、动态库、解码器及语言服务 | 通常随 App 打包、审核并通过版本更新发布，不能预设成使用时下载执行的原生插件；内置帮助进程、运行时与沙盒能力仍需验证 |
| 字体、词库、模板、供内置能力使用的模型等资源 | 可以评估按需下载；需按资源本质和平台规则确认，不能把可执行代码简单改名为资源包 |
| 已内置功能的付费启用 | 可以评估 App 内购买；解锁功能不必重新下载引擎 |
| 分享扩展、Quick Look 等系统 App Extension | 随包含它的 App 打包分发，不作为任意下载后安装的原生插件 |
| HTML5／JavaScript 小程序或插件 | Apple 有专门规则，不能据此推导任意原生解析库也可动态下载；本项目尚未选择此路线 |

依据：[App Review Guidelines 2.5.2、4.7](https://developer.apple.com/app-store/review/guidelines/)、[Apple Bundle 内容布局](https://developer.apple.com/documentation/bundleresources/placing-content-in-a-bundle)。

Apple Background Assets 支持按需获取资源，可选择 Apple 托管或自行托管。采用前需确认目标系统版本、资源保留与重新下载行为。该机制解决资源分发，不自动解决原生可执行代码分发限制。

参考：[Background Assets](https://developer.apple.com/documentation/backgroundassets)。

**此前建议，尚未确定**：格式引擎内部模块化并随 App 发布；新增格式通过版本更新交付；只有体积明显较大的可选数据再考虑下载。这样可以减少自建下载服务的需要，保留本地处理方向。

## 3. 离线与联网边界

“离线”需要拆分为文件处理、资源获取、购买和外部内容访问，不能用一个标签替代全部行为。

| 场景 | 联网情况与产品边界 |
| --- | --- |
| 打开设备已有文件、阅读、解压、压缩 | 目标是在本地完成，无需上传原文件 |
| 下载可选资源包 | 下载时需要网络；完整资源保留在设备后，依赖它的处理可设计为离线执行 |
| App 安装和版本更新 | Apple 当前方向为应用商店，其他端渠道待定；不等于应用自建文件处理服务 |
| 购买和恢复购买 | Apple 需考虑商店服务联网，其他端按选定模式设计；购买后核心阅读、编辑和压缩应可日常离线使用 |
| 预览本地 HTML 及同目录图片、CSS | 可以本地完成，需维护正确的相对路径和资源访问范围 |
| HTML 引用远程图片、字体、脚本、API | 完整效果可能需要网络；禁用时应合理提示缺失资源，策略待定 |
| 云盘、账户、同步、在线转换、远程语言服务、服务端 OCR／AI | 尚未确认为需求；不因 HyHub 有账号/远控就自动加入本项目 |

可选下载不要求上传用户文件。若最终包含可选下载，应准确描述为“文件处理在本地完成，部分可选资源需要联网下载”，而非宣称整个应用任何环节都绝不联网。

目前没有选择云端格式转换来弥补本地格式缺失。以后如果考虑，需要重新确认产品定位、费用、隐私与上架要求。

## 4. Apple 个人开发者与发布方式（历史专项）

用户希望：使用个人 Apple 开发者身份，尽量减少设立公司及额外证书、许可和服务成本。

### 4.1 本机安装、TestFlight 与公开上架

- 自用真机开发安装、TestFlight 和 App Store 公开发布是不同路线，不应混为一谈。
- TestFlight 适合测试，不能当作无期限公开商业发行的替代方案。
- 本项目目前讨论的是有可能公开收费的产品，不是已经决定仅自用或仅 TestFlight。

### 4.2 个人收费应用

- Apple 个人开发者身份可以用于发布普通付费工具；不能仅因为收费就认定必须注册公司。
- 讨论时参考的中国大陆 Apple Developer Program 年费为 **人民币 688 元／年**，正式开通或续费时以 Apple 当前结算为准。普通组织开发者计划与 Enterprise 内部分发计划是不同产品。
- 付费下载及数字功能解锁需要相应协议、银行与税务资料；卖方身份展示、税务义务也需纳入发布准备。
- App 内数字功能解锁通常使用 Apple App 内购买；买断、分功能购买、订阅及具体售价尚未确定。
- Apple 会员费不等于全部经营成本，另有平台佣金、税费及可能的设备、SDK、服务与人工成本。佣金应按届时适用的地区、平台及已获批准的计划核实，不固定套用某个比例。

参考：[Apple 开发者注册](https://developer.apple.com/cn/help/account/membership/enrolling-in-the-app/)、[App Review Guidelines 3.1](https://developer.apple.com/app-store/review/guidelines/#payments)。

### 4.3 资料准备方向

候选准备项包括：应用身份和签名、App Store Connect 信息、截图和描述、年龄分级、隐私政策及隐私披露、支持联系方式、收费所需协议与收款税务资料，以及审核中需要的操作说明或访问条件。

这些资料不等于都要额外购买“证书”。普通工具的公开上架要求，也不能直接套用新闻、游戏、在线出版等特定业务的资质要求。

参考：[App Store Connect 应用信息](https://developer.apple.com/cn/help/app-store-connect/reference/app-information/app-information/)。

## 5. 国内备案、许可与软件著作权

本节保留讨论的关键边界，具体商业方案确定后再针对实际业务核实。

### 5.1 离线不自动构成免备案结论

工信部 APP 备案规定围绕在境内从事互联网信息服务的 APP 主办者展开。应按应用实际提供的服务及分发要求判断，不能只按“发出过网络请求”或“只下载一次资源”做结论。

本地读取用户自有文件，与提供在线内容库、账户服务、云转换或同步的业务不同。但目前没有取得本应用具体方案的免备案确认，不能把“本地工具”直接写成已经确认免备案。

资源由 Apple 托管，也不能据此推导应用必定免备案。APP 备案、网站备案、经营性互联网信息服务许可是不同问题，不能混称为一个“ICP 证”。

参考：[工信部 APP 备案通知解读](https://www.miit.gov.cn/jgsj/xgj/hlwgl/art/2023/art_564bf0759d7e41d5b4aa8ce4996b9e84.html)、[Apple 中国大陆应用信息要求](https://developer.apple.com/cn/help/app-store-connect/reference/app-information/app-information/)。

### 5.2 阅读文件不等于提供出版服务

用户导入自己的本地电子书或文档进行阅读，与经营线上书库、销售或传播出版内容是不同业务。不能仅因支持 EPUB、PDF 或漫画，就推导必定需要网络出版许可；若后续加入在线内容服务，应重新核实。

参考：[网络出版服务管理规定](https://www.nppa.gov.cn/xxgk/fdzdgknr/zcfg_210/bmgz_213/202112/t20211209_442163.html)。

### 5.3 软件著作权登记

软件著作权登记不应被当作所有普通 iOS 工具上架都统一强制提供的前提。软件、图标、字体、第三方引擎等仍需具备相应权利或授权；如分发平台针对具体情况要求权属材料，再按要求准备。

讨论时查到的官方办事信息显示，软件著作权登记费已停征；如选择代理服务，其收费不等于官方登记费。具体办理流程和材料应以届时官方指南为准。

参考：[计算机软件保护条例](https://xzfg.moj.gov.cn/mobile/law/detail?LawID=581)、[北京市政务服务软件著作权办事问答](https://banshi.beijing.gov.cn/pubtask/task/1/110000000000/3e283672-76be-4c8c-98e8-0bebe9bd06bf.html?locationCode=110000000000&serverType=1002)。

### 5.4 不把个人账号等同于永久免经营登记或免税

Apple 接受个人卖方，不自动解决中国大陆所有经营登记、税务和特定业务许可问题。应结合实际经营规模、业务性质与当时适用规则判断；如果未来需要经营主体，也不能直接认定唯一选择是成立公司。

当前没有为本项目办理、申请或购买任何资质。

## 6. 市场与商业方向

此前判断：有成为个人开发者长期经营工具的可能，但竞争充分，不能从同类软件数量直接推出销量或盈利。

已查到的商店介绍中，存在同时列出文档／HTML 预览、压缩包浏览、解压、创建压缩包等功能的产品，也存在宣传离线、无账号、无广告的产品。这些是开发者自述，尚未实测，不能当作其兼容性或隐私表现已经验证。

参考：[解压专家](https://apps.apple.com/cn/app/id1493708052)、[智能解压专家](https://apps.apple.com/cn/app/id6756837927)。苹果系统“文件”也已支持基础 ZIP 压缩与解压：[Apple 官方说明](https://support.apple.com/en-us/102532)。

建议重点验证的价值：

- 从接收文件到预览、提取、重新打包、分享的操作是否顺畅。
- 本地 HTML 与配套资源能否正确呈现。
- 压缩包中的文档、图片等能否按需查看。
- 广泛格式覆盖是否有真实兼容样本支撑。
- 大文件、中文文件名、失败提示和缓存管理是否可靠。

此前提出过买断，或免费基础能力加一次性解锁的方向，均未定稿；“无广告、无账号”也只属于讨论中的候选承诺，不能当作已经批准的完整商业模式。

## 7. 成本和排期记录

以下均是讨论中的工程估算，不是报价、承诺或正式排期：

| 范围 | 讨论估算 | 前提与限制 |
| --- | --- | --- |
| 较窄的 PDF／TXT／图片阅读器 | 原先讨论过约 3～6 周的可上架首版 | 范围明显小于用户目前想要的产品，不可继续用作完整项目估算 |
| 有边界的文档、HTML、常见格式与压缩管理首版 | 约 8～12 周 | 假设一名熟悉 Apple 平台与 Swift/Rust 的开发者全职投入，复用成熟组件，范围明确 |
| 较广格式且兼容性更扎实的版本 | 原先讨论过约 3～6 个月 | 不代表本需求完整格式表可在该时限内全部高质量覆盖；专业格式仍需另评估 |
| 全部候选格式及复杂变体 | 没有可靠总工期 | 需先完成格式、引擎、授权、平台和体验的验证，再分阶段估算 |

上表是当时 Swift + Rust、macOS/iOS 范围的讨论值，不作为当前全端原生、编辑与代码智能需求的工期。新增宿主、绑定、引擎兼容及各渠道需单独验证和估算，见[分阶段实施](ROADMAP.md)。

已有 Mac 和测试设备、自己投入开发、使用适当的系统能力或允许的开源组件、无需自建后端时，固定现金投入可以较低。但不能据此说整个商业产品的总成本只有 Apple 年费。

可能的持续投入包括：开发与兼容性维护、真机测试、商用 SDK 或引擎授权、资源托管、隐私与支持页面、用户支持、平台佣金和税费。是否产生各项费用取决于最终方案。

## 8. 下一阶段建议与未决问题

1. 先稳定 macOS 骨架与 Rust 核心契约，按全端规划逐个验证宿主、系统版本、架构和原生交互；Apple 先只走商店的约束不自动决定其他端渠道。
2. 维护[格式台账](FORMAT_SUPPORT.md)，将读取、预览、交互、提取、创建、编辑和平台分别列明。
3. 对各大日常类别做代表性验证，同时单独评估专业格式和复杂变体。
4. 形成引擎及授权清单，再估算安装体积、运行资源、开发成本和排期。
5. 决定是否存在资源下载、远程网页访问、账号或云端能力，形成真实联网清单。
6. 根据明确后的业务范围复核国内上架、备案、经营与税务要求，再确定商业方案。

当前已有 macOS SwiftUI + Rust/UniFFI ZIP 列目录骨架，全端原生与浏览编辑为产品方向。其余宿主、格式支持深度、原位置项目模式、语言服务、最低版本、渠道、价格、资源包与日期尚待落实。本次仅更新文档，未迁移 HyHub 代码、修改功能、构建、安装、发布或提交推送。
