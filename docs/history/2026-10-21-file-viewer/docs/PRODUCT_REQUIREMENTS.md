# 产品需求与格式范围

> **2026-10-21 编辑器方向更新**：最新定位改为轻量、原生、完全开源的代码编辑器，借鉴 IDEA 界面组织。先读 [新方向与优先级](EDITOR_DIRECTION.md)；本文旧文件浏览器主线、强制复制入库、付费解锁及商店优先规则遇冲突时仅作历史记录。候选能力和骨架实现状态仍需分别看待。

初始记录：2026-10-19；更新：2026-10-21。来源：本项目既有讨论，以及从 HyHub 文件模块讨论延续的独立项目需求。

## 1. 文档状态

本项目定位为**独立、全端原生的万能文件浏览编辑器**。已有 macOS + Rust ZIP 目录浏览骨架，其他能力仍按阶段实现；目录名 `hc_file_viewer` 不代表最终产品名称。

2026-10-21 用户明确要求把文件浏览/编辑及代码智能方向独立到本项目，全端原生开发。该指示更新此前“仅 iOS/macOS”的平台范围，并把文本与代码编辑纳入产品方向；没有要求本轮迁移源码或一次实现全部格式。

- **已明确**：用户直接提出的产品目标或约束。
- **讨论方向**：由对话上下文形成的倾向，细节仍需确认。
- **建议**：助手提出的方案，尚未被逐项批准。
- **待确认**：影响开发、商业或上架的未决问题。

本记录只收录文件浏览编辑器相关需求。HyHub 的账号、设备监控、云盘和远控不自动成为本项目范围；可参考能力见 [HYHUB_REUSE.md](HYHUB_REUSE.md)。

## 2. 用户表达与产品目标

用户明确表达：

> “什么格式都支持浏览，html那些能预览而不是看文本，还有各种压缩包……也可以做压缩包……文档浏览也要有。”

在只列出 PDF、Office、HTML、Markdown、图片和常见压缩格式后，用户指出：

> “这些格式感觉也还是不够的吧。”

因此，产品规划需要保留广泛覆盖文件类别的目标，不能擅自缩减为少数格式的阅读器或只有解压功能的工具。

产品希望解决的问题：收到文件后，在同一个应用完成查看、阅读、浏览压缩包、选择性解压、整理、文本与代码编辑、重新压缩和分享。代码补全、定义/引用跳转作为增强方向，不让 IDE 工具链成为普通文件功能的前置条件。

“什么格式都支持”是覆盖方向，不是当前可对外承诺的兼容性结论。必须建立可验证的支持清单，标明格式版本、支持操作和限制。

## 4. 候选格式范围

以下是产品目标清单，不是已经实现或已经验证的兼容表。每个格式还需要确认解析方案、授权、版本差异和预览深度。

| 类别 | 候选格式 | 目标浏览方式 | 需要验证的重点 |
| --- | --- | --- | --- |
| 办公与固定版式文档 | PDF、DOC/DOCX、XLS/XLSX、PPT/PPTX、RTF、ODT/ODS/ODP、Pages、Numbers、Keynote、XPS | 按排版预览，支持翻页、工作表或幻灯片切换 | 字体、复杂排版、加密文档、多页、大文件；预览不等于执行宏或重新计算所有公式 |
| 网页与阅读文档 | HTML/HTM、Markdown、MHT/MHTML | 渲染正文、图片、样式、目录和链接；源码可作为附加视图 | 本地相对路径、资源目录、中文编码、脚本、远程依赖；MHTML 需单独评估 |
| 电子书与漫画 | EPUB、MOBI、AZW3、FB2、CBZ、CBR | 章节目录、阅读进度、字号调整或漫画翻页 | 排版、封面、目录、图片顺序；受 DRM 限制的文件不直接承诺支持 |
| 图片 | JPG/JPEG、PNG、GIF、HEIC/HEIF、WebP、BMP、TIFF、SVG、AVIF、ICO，以及部分相机 RAW | 静态图、动图、多页图片、缩放与信息查看 | 色彩、方向、透明度、超大图、RAW 子类型和系统版本差异 |
| 音频 | MP3、AAC、M4A、WAV、FLAC、OGG 等 | 播放、定位、封面、元数据 | 容器与编码组合、时长、拖动、后台播放是否纳入范围 |
| 视频与字幕 | MP4、MOV、MKV、AVI、WebM；SRT、ASS、VTT | 视频播放、字幕加载、进度恢复 | 内部音视频编码、字幕样式、HDR、硬件解码及耗电 |
| 压缩与归档 | ZIP、RAR、7z、TAR、GZ、BZ2、XZ、ZST、CAB、TGZ/TAR.GZ 等 | 浏览目录、按需查看内部文件、解压、选择性导出 | 加密方法、密码、分卷、嵌套归档、中文文件名、损坏文件、大包 |
| 镜像及安装包容器 | 部分 ISO、APK、IPA 等 | 在适用时查看目录、元信息或可提取内容 | 识别容器不等于运行、安装或完整解析其中的应用；DMG 等另行评估 |
| 代码与配置 | 常见源码、TXT、LOG、JSON、XML、YAML、TOML、INI 等 | 阅读、原生编辑/保存、高亮、搜索、行号、结构折叠；按语言增强补全与导航 | 编码、超长行、大文件、项目环境及语言服务；不默认运行代码 |
| 表格与结构化数据 | CSV、TSV、JSONL、SQLite 数据库 | 表格、树形结构、数据库表与记录查看 | 分隔符、编码、数据量；`.db` 扩展名不代表一定是 SQLite |
| 邮件与个人资料 | EML、MSG、VCF、ICS | 邮件正文与附件、联系人、日程信息 | 各格式解析器、附件、字符集、远程资源；不默认导入系统通讯录或日历 |
| 字体 | TTF、OTF、WOFF、WOFF2 | 字体信息、示例文字和字符预览 | 字体解析、字形覆盖、预览与系统安装的区别 |
| 设计与出版文件 | PSD、AI、EPS、CDR、DjVu、CAJ 等 | 视格式提供合成预览图、页面或内容预览 | 合成图与完整图层解析不同；部分格式需要专门引擎或商业授权 |
| 工程图与三维模型 | DWG/DXF、STL、OBJ、GLB/glTF、USDZ、STEP/IGES 等 | 二维图纸或三维模型浏览 | 外部引用、材质、单位、版本、模型规模和引擎授权 |

专业格式是否纳入首版尚未确定。不能仅凭系统能显示某个缩略图，就宣传该格式已经完整支持。

各类别的实际实现状态在 [FORMAT_SUPPORT.md](FORMAT_SUPPORT.md) 单独维护。此表中的“目标”不代表现有 ZIP 骨架已经支持这些格式。

## 5. “支持”的产品定义

需要按格式分别记录以下能力，不能只提供一个“支持／不支持”开关：

1. **识别**：知道文件类型、大小、基本属性。
2. **内容预览**：能展示正文、图像、页面、音视频或模型。
3. **内容交互**：按适用格式提供搜索、目录、工作表切换、章节跳转、模型旋转等。
4. **提取或导出**：例如提取压缩包条目、保存附件；不同格式分别约定。
5. **创建或编辑**：文本、代码、Markdown/HTML 编辑纳入方向；其他类别逐项确认，不能从能预览推导可无损编辑。

压缩包的读取、解压、创建、加密创建、分卷创建需要分开记录。RAR 解压能力不能直接推出 RAR 创建能力。

对本身存在视觉或结构表现形式的格式，应优先提供对应视图：HTML 是网页，CSV 是表格，JSON 是结构树，EPUB 是阅读界面，图片是图像，视频是播放器。查看源码可以保留为附加能力。

## 6. 重点使用流程

以下是产品设计与验证场景，具体界面仍需实现和验收。

### 6.1 接收压缩包并阅读文件

从聊天软件分享菜单或系统“文件”导入压缩包 → 浏览目录 → 找到文档、图片或网页 → 预览所需内容 → 选择性解压或分享。

产品体验上的“直接浏览压缩包”不意味着底层绝对零解压。预览时允许按需提取必要文件到本地受控目录，避免要求用户手动全部解压后再寻找内容。

### 6.2 阅读本地 HTML 报告

导入包含 HTML、CSS、图片等资源的文件夹或压缩包 → 打开主页面 → 显示排版、图片、目录和内部链接 → 按需查看相关附件。

必须区分本地资源和远程资源。是否允许远程脚本、图片、字体或请求，以及如何提示用户，仍待确定，不能默认宣称任何网页都能完整离线运行。

### 6.3 整理文件并重新打包

选择多个文件或目录 → 选择创建格式和可选参数 → 展示处理进度 → 生成压缩包 → 通过系统分享或保存导出。

具体创建格式、密码加密、压缩等级和分卷是否进入首版，待验证后确定；ZIP 是此前提出的优先候选，尚非最终决定。

### 6.4 持续阅读与管理

再次打开文件 → 找回最近阅读位置或目录 → 继续阅读 → 按需查看文件信息、搜索内容或导出。

最近文件/目录是首页方向；书签、收藏、阅读进度、排序和批量管理的细节继续按阶段细化。

### 6.5 就地预览与持续编辑

桌面文件库保持当前目录、选择、排序、筛选和滚动状态。设计基线为：单击选中，双击文件或空格打开快速预览；双击目录进入目录。“在工作台打开”或“编辑”把同一文档会话提升为标签，不重新读取并丢弃状态。

关闭预览、切换标签或从定义跳转返回，都能回到原浏览/编辑位置。独立窗口作为用户主动选择的宿主，不因打开普通文件自动拉起。大屏移动端可分栏，窄屏使用可返回的预览/编辑页面，保留来源状态。

### 6.6 文本编辑与保存

导入文本 → 编辑库内副本 → 撤销/重做、查找替换 → 保存到文件库 → 按需导出。Markdown/HTML 可并排查看效果；预览默认不执行不受控脚本。

未保存关闭时提供保存、放弃、取消；保存失败保留内容。外部变化、只读、编码无法往返和导出目标冲突分别处理。读取预算超出时退回只读/分段浏览，不能保存截断内容。PDF、Office、图像可视化编辑和批注另列范围。

压缩包内条目先按需预览；选择编辑时提取为独立库内副本，保存不自动回写压缩包。原位归档编辑和重新打包替换另行设计。

### 6.7 代码补全与导航

打开代码文件即可使用基础编辑和高亮；完整语义能力依赖语言服务及项目上下文。定义跳转进入目标标签并记录回退位置，查找引用先显示结果列表。补全、悬停、索引状态和失败提示不抢走输入焦点，不阻塞编辑。

复制入库的单文件不具备完整原项目上下文。项目目录快照、原位置工作区、Git 访问边界先做决策，再实现项目级索引，见 [CODE_INTELLIGENCE.md](CODE_INTELLIGENCE.md)。

## 7. 产品形态与界面设计方向

保留 2026-10-19 已明确的文件库语义，结合 2026-10-21 独立全端方向更新；桌面/移动端具体交互属于本轮设计基线。

### 7.1 信息架构

已明确：

- 启动首页展示最近打开的文件与目录，支持继续访问内容。
- 除最近列表外，提供应用内文件保存区（内部文件库），用户可以把文件存入应用内统一管理和查找。
- 做内部文件库的原因：系统“文件”App 在查找和管理文件上的体验不能满足需求。
- 所有打开过的文件一律复制入库，不做原位置引用；外部引用容易产生路径失效、权限变化等问题，已明确不采用。
- 分享菜单、“文件”App 等各入口打开文件时同样复制入库。
- 库内同时支持两种组织方式：多级目录（文件夹），以及参考 macOS 颜色标记体系的标签。
- 最近记录目标为本地持久化，不人为设固定总条数上限；列表分页和展示预算另定，历史讨论值为 1000 条。当前骨架使用 JSON，全量内存载入不作为最终方案。
- 入库副本保留来源信息。

桌面设计基线：文件库默认网格，可切回列表并记忆选择；右侧快速预览可拖动宽度，提供清晰的折叠/展开与提升工作台按钮。宽度可参考 HyHub 的窗口 1/4～2/3 范围，但需要结合最小可用内容宽度和窄窗口重新验收，不在移动端机械套用比例。

待细化：

- 目录与标签的具体交互（打标方式、按标记筛选等）。
- 最近列表的排序方式，以及超出展示上限后的清理策略（候选上限 1000 条，数值待实现时确定）。
- 来源信息之外保留哪些元数据（原路径、导入时间、导入入口等）。

### 7.2 界面与交互原则

已明确的风格方向：

- Apple 使用 Apple 原生控件，其他端遵循各自原生设计语言，不把 macOS 菜单、侧栏和键盘动作直接照搬到手机。
- 交互动效要连贯流畅，界面与动效质量以麦当劳 App 的移动端体验为参考。
- 减少文字，多用图标，交互逻辑清晰。
- 功能克制，不做功能堆砌式界面，入口与层级按常用程度取舍。
- 加载态及时可见；压缩/解压与索引有阶段、可用进度、取消和结果反馈，界面仍可操作。
- 桌面系统右键可规划压缩包解压、文件/目录/多选压缩及紧凑任务窗；移动端使用文件选择与系统分享入口。各端扩展、权限及是否先入库分别设计，不默认继承 HyHub 已安装的系统服务。

### 7.3 技术分层方向

已明确：

- Rust 承担平台无关处理：归档、格式解析、编码、编辑事务、任务与缓存等，通过绑定向各平台提供能力。
- 优先 Rust crate；成熟系统能力或 C/C++ 引擎按效果、性能、许可与平台覆盖选择，不要求所有分析器重写为 Rust。
- 共享核心按目标平台重新构建和验收；原生渲染、权限、UI、系统扩展与生命周期分别适配。

建议（未定稿）：

- Apple 继续已有 SwiftUI + UniFFI 骨架；其他端建议 WinUI、GTK、Compose、ArkUI，具体见技术设计。
- 不让可选 LSP、专业格式引擎或下载资源成为所有普通文件操作的强制前置条件。

## 8. 体验与质量要求建议

- 文件导入后应能找到其位置、来源和导出入口，避免产生难以理解的重复副本。
- 中文文件名和常见文本编码应作为真实兼容测试的一部分。
- 大文档、大图片、大压缩包需要观察首屏时间、内存、临时空间和操作中断恢复。
- 提取、打包和其他耗时任务应有明确进度、取消能力和失败原因。
- 普通大包不设置任意固定字节和总时长上限；以流式 I/O、64 位大小/偏移、分页、内存预算及磁盘检查控制资源，取消不破坏原件。
- 格式不支持、密码错误、文件损坏、缺少资源和内存不足，应提供可理解的不同反馈。
- 本地预览和解压不应默认把用户文件上传给服务端。
- 临时提取文件、缓存和用户原始文件需要可区分，清理不能误删原件。
- 兼容性记录要覆盖真实样本，不能只用少量自制正常文件证明一个格式“全部支持”。

格式支持表见 [FORMAT_SUPPORT.md](FORMAT_SUPPORT.md)，逐项记录引擎、许可、格式版本、平台、操作、样本与限制。相同扩展名不等于相同兼容性，桌面通过也不代表移动端通过。

## 9. 范围与推进方式

用户尚未确认首版边界，不应把助手提出的窄范围 MVP 当作定稿。

建议先完成各大日常类别的代表性文件验证，形成广泛覆盖的首版候选范围；同时对专业格式、复杂变体建立后续计划。新增格式应优先补足真实使用场景，不能只累加扩展名数量。

首版和后续版本均以格式支持表及实际验收为准。推进建议见 [ROADMAP.md](ROADMAP.md)；旧 Apple 双平台工期不作为全端估算，当前没有正式排期。
